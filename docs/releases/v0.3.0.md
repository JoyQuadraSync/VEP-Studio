## Product Milestone

VEP Studio v0.3.0 marks the transition from a linear workflow runtime to a deterministic Decision Workflow Platform.

The release combines the strongly typed Event Platform, Workflow Definition System, immutable Workflow Runtime, and declarative conditional branching into one coherent product milestone.

## Architecture Summary

```text
Event Platform                         Workflow Platform
──────────────                         ─────────────────
Strongly Typed Events                  WorkflowDefinition
Concurrent EventBus                    WorkflowValidator
ExecutionContext                       WorkflowRegistry
PublishResult                          WorkflowRunner
SubscriberResult                       WorkflowExecution
                                       OperationRegistry
                                       ConditionEvaluator
```

WorkflowRunner owns workflow control flow. EventBus does not evaluate conditions, select branches, or store mutable workflow execution state.

```text
EventBus                 WorkflowRunner
└── ExecutionContext     └── WorkflowExecution
```

`ExecutionContext` remains event-publication-specific. Workflow executions remain immutable snapshots with no shared mutable state.

## Decision Workflow Capabilities

- decision input passes through as decision output
- decision steps produce normal completed step results
- all conditional edges are evaluated before selection
- one matching condition selects one edge
- zero matches may select one explicit default edge
- multiple matches fail rather than use edge order
- no-match and evaluation failures are explicit
- edge declaration order does not determine behavior
- existing linear workflows remain compatible

## Condition Language

The condition language is intentionally limited to:

- `equals`
- `not_equals`
- `greater_than`
- `greater_than_or_equal`
- `less_than`
- `less_than_or_equal`
- `exists`
- `not_exists`
- `and`
- `or`
- `not`

Conditions are declarative and serializable. They do not contain callbacks, scripts, dynamic evaluation, regex, arithmetic, templates, functions, or user-defined operators.

Conditions can read only approved deterministic snapshot data:

- workflow input
- current decision-step input and output
- completed-step input, output, status, and structured failure code
- execution ID, workflow ID, workflow version, and workflow state

They cannot access time, randomness, environment variables, EventBus state, network or database state, mutable globals, or arbitrary services.

## Branch Selection Semantics

```text
evaluate every conditional edge
              ↓
matching edge count
├── 1  → select the matching edge
├── >1 → multiple_matching_branches
└── 0
    ├── unique default → select default
    └── no default     → no_matching_branch
```

A default edge contains no condition and is selected only when no conditional edge matches.

Logical `and` and `or` evaluate every child in v0.3.0 so malformed condition data cannot remain hidden behind short-circuit behavior.

## Failure Semantics

- `condition_evaluation_failed` — a condition cannot be evaluated from approved snapshot data
- `multiple_matching_branches` — more than one conditional edge matched
- `no_matching_branch` — no condition matched and no default exists
- `invalid_default_branch` — the decision contains an invalid default or unconditional edge configuration

Failures contain stable structured workflow information and do not retain raw exceptions, causes, stacks, rejection values, or arbitrary handler data.

## Backward Compatibility

Existing linear workflows remain fully compatible:

- start and action steps retain one unconditional outgoing edge
- finish steps retain zero outgoing edges
- existing operation resolution and handler semantics remain unchanged
- WorkflowExecution retains immutable snapshot behavior
- existing EventBus and HTTP behavior remain unchanged
- existing ExecutionContext remains unchanged

## Known Limitations

- parallel workflows are not supported
- workflow execution is in memory only
- persistence and recovery are not implemented
- retry, timeout, cancellation, and dead-letter policies are not implemented
- human tasks and AI agents are not implemented
- no visual workflow designer exists
- workflow execution is not exposed through HTTP
- condition operators are intentionally limited
- nested workflow values are not deep-frozen
